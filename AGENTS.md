# Project agent memory

**This repo's purpose: run nested sampling (PolyChord) over the parameter space of R2D2 and WSClean to find their failure modes.** Everything else (Docker images, smoke tests, pinned upstream revisions) exists to serve that. It is not a paper-reproduction or benchmarking harness.

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `./ri` (the `ri` file at the repo root) is the front door and the only entrypoint users are pointed at: stdlib `argparse` that turns flags into the environment variables `scripts/lib/defaults.sh` already reads, then dispatches into `scripts/`. It holds no behaviour - new behaviour goes in a script, with a subcommand added in `ri` and a case in `scripts/test_cli.py`. The one exception is `./ri tui` (`tui/`), a Bubble Tea front end over `./ri runs`, `./ri health` and `./ri search` - the only Go here, and the only command that needs a toolchain the rest of the repo does not. `./ri --dry-run <command>` prints what it would run.
- Nested-sampling infrastructure, run commands, and the per-stage profiler (`./ri profile <run>`) are documented in `docs/nested-sampling.md`, with `docs/run-health.md` for reading a live run, `docs/robustness.md` for what happens when one breaks and `docs/nested-sampling-throughput.md` for why the ranks idled (and why searches now run PolyChord's asynchronous MPI mode by default), why rank 0 is not one of the workers, why a rank past the first few is worth ~40% of one, why WSClean is built for `x86-64-v3` by default (`WSCLEAN_TARGET_CPU`, worth ~9% of the `wsclean` binary against the plain x86-64 baseline, and `--native` is now only a few percent on top), why a source at the phase centre no longer asks MeqTrees for its (constant) predict, why the simulator no longer writes `WEIGHT`/`SIGMA` either (makems already leaves them at 1.0, so the sigma reaches R2D2 as `ms_to_r2d2_mat.py --noise-sigma-jy` out of `simulation.json` - a third of the simulate stage, guarded by `self_check_noise_weighting`), and where the remaining per-evaluation budget goes (86% is the `wsclean` binary - and the profiler's `image_container_overhead` line is mostly GNU `time`'s 10ms clock, not a cost - and the 2.2x concurrency inflation is this CPU's all-core clock and hybrid topology, not a memory-bandwidth ceiling - so read any throughput measurement after the first ~4 seconds, which run 20% fast), and why a scored evaluation's `sim.ms` is never written to the disk at all (it is built in `NS_SCRATCH_DIR`, one host tmpfs bind-mounted into every container, and deleted as `metrics.json` is written; only a failed evaluation and `./ri search --keep-measurement-sets` move it back beside the record), and why a resume holds only each adopted evaluation's objective rather than its record (every rank runs the adoption, so keeping the records wanted 62GB on a 62GB host at the target run size), and why a bigger run is a *more* efficient one (utilisation 93.9% at `--nlive 25` and 98.3% at `--nlive 200`, because the unaccounted time is a ~6s per-run startup constant plus 0.8%, not a rate - PolyChord's own sampling is 5us a call at every `nlive`, so do not go looking for idle time again); and `docs/nested-sampling-power-limit.md` for why the host rather than the code is what caps throughput now - the package runs at a 65W RAPL long-term limit against the part's own 117W rating, which is what sets the all-core clock, costs ~26% of the evaluations per second, is raisable only as root, and is the real cause of the burst-clock trap (the limit's averaging window is 8 seconds, not 4); and `docs/nested-sampling-io-placement.md` for where an evaluation's bytes go - the simulator assembles the MS in the destination directory when that is already `NS_SCRATCH_DIR` (`scratch_root_for()`, because a container's own `/dev/shm` and the shared scratch are different mounts, so the closing move was a whole-MS copy: -6.5ms an evaluation), WSClean's `-temp-dir` and its five FITS images are free where they are, `--mpi-procs` above `nproc` buys nothing at a fixed power limit, and A/B arms run *sequentially* on this host produce consistent false positives at the ~4% level - run them simultaneously; and `docs/nested-sampling-evaluation-budget.md` for what one evaluation's ~280ms is made of at production concurrency, reproduced on two seeds straight out of every `wsclean.stdout.log`'s own phase line - 69% is WSClean's clean loop, 20% the path to the first inversion, 11% starting the process (casacore's static initialisers; dropping MPI, Python or HDF5 from the build was measured and buys ~0), 6% simulate and 0.6% metrics, so nothing measurable is left in the harness - plus the simultaneous-arm flag screen that closes off WSClean's own knobs (`-parallel-reordering 1` and `-abs-mem` are worth 0, `-no-reorder` costs 36%, the whole reorder is only 5% and is not reusable across evaluations, and `-wgridder-accuracy 1e-2` is worth +13.8% but must not be taken because `log10_dynamic_range` reaches 1e6) - plus the `/proc/cpuinfo` trap (a *cold* open blocks ~20ms on this kernel and a warm one 0.04ms, so warm it before any rig) and the fact that R2D2 has never been profiled here at all, because `./ri fetch-checkpoints` needs a browser; and `docs/nested-sampling-clean-loop.md` for the one lever that does move the clean loop - `-mgain` sets how deep each minor loop goes, so `-niter 100` buys ~6.5 major cycles at 0.8 and ~4.7 at 0.9, worth +20% evaluations per second, left at `DEFAULT_WSCLEAN_MGAIN = 0.8` because it is result-preserving for the default `total_rms_jy` objective (1e-7 median) but not for `peak_flux_abs_error_jy` or `sigma_res`, and because it is the experiment definition every archived run was scored under; and `docs/nested-sampling-ms-open.md` for the largest item outside the gridding itself - WSClean re-opens the *parent* Measurement Set once per gridding and degridding pass (15.7 times an evaluation) and casacore attaches every subtable on each open, so the simulator now deletes the six nothing reads (`FEED`, `FLAG_CMD`, `HISTORY`, `POINTING`, `PROCESSOR`, `STATE`), worth +14.9% evaluations per second end to end for the first five and another -3.2% on the `wsclean` binary for `FEED`, with bit-identical images - dropped after the predict rather than in the cached skeleton because casacore refuses to open an MS missing a required subtable and MeqTrees needs it opened that way; the avenue is now closed from the simulator's side, because each of the six survivors was dropped on its own and every one kills WSClean, their unused columns cannot be stripped either (casacore's `MS*` classes validate them) and `IncrementalStMan` will not release a main-table column - so the floor is ~1.9ms an open and ~30ms an evaluation, and a `--keep-measurement-sets` MS is one CASA will not open; and `docs/nested-sampling-wsclean-patches.md` for the other half of that item, which is WSClean's - it re-opens the parent MS on every pass only to read the `ANTENNA` table's names, so `docker/wsclean/patches/` now carries a one-function cache for them (`git apply`ed in `docker/wsclean/Dockerfile`, hashed into `ri.build-inputs`, and a `WSCLEAN_GIT_TAG` bump that breaks a patch fails the image build on purpose), worth +10.5% evaluations per second end to end and -13.1% on the `wsclean` binary with bit-identical images - and note that `WSCLEAN_IMAGE` lets two searches A/B two `wsclean` builds simultaneously, and that `NS_MAX_NDEAD` defaults to 12, so a benchmark search that forgets `--max-ndead` finishes in four seconds. Use those entrypoints instead of ad hoc container wiring.
- The `polychord` and `meqtrees` images both bake in files from `scripts/lib/nested_sampling` at build time (no live mount); after editing those files, rebuild every image that copies them (`scripts/build.sh polychord`, `scripts/build.sh meqtrees`) before starting a nested-sampling run, or it silently runs the stale baked-in code (`./ri search` and `./ri resume` both build first, so this bites a run started any other way, or one resumed with `--no-build`). The exception is `r2d2_serve.py`, which the R2D2 sidecar runs off the repo bind mount, so it needs no rebuild. `polychord` copies the whole directory, `meqtrees` only the three simulate-side scripts (`simulate_point_source_ms.py`, `point_source_forest.py`, `ms_to_r2d2_mat.py`) - except that the `meqtrees` build also bind-mounts `common.py` and `defaults.toml` to bake the MS skeleton cache, so a parameter-space change (`[[parameter_space]]` in `defaults.toml`, the one authoritative copy) needs both images rebuilt.
- `scripts/build.sh` hashes each image's build inputs into an `ri.build-inputs` label and skips `docker build` when nothing changed (~0.08s), so rebuilding freely is cheap; the input list lives in `build.sh` and must be updated whenever a Dockerfile starts copying something new.
- Host `__pycache__` is excluded from both the context (root `.dockerignore`) and the build-input hash, so a `--self-check` does not force a rebuild.
- Image tags are shared across worktrees. Capture `docker images -q <tag>` per timing run and rebuild all images before trusting a result if another session could have rebuilt one.
- Memory, not CPU, caps a run: ~3.4GB per R2D2 rank (~0.2GB per WSClean rank), linear in `NS_MPI_PROCS` and independent of `NS_NLIVE`, so raise `--nlive` freely and size `--mpi-procs` to fit. `scripts/lib/rank-budget.sh` clamps and reserves against free memory, and reaps sidecars a killed run left holding it (`ns_reap_leaked_sidecars`) - "killed" meaning the run, not its launcher shell, which is why each sidecar carries an `ri.run-dir` label and a container whose labelled run is still live is never reaped. Sessions share this host, so expect another session's run to shrink yours. Run directories: the default is claimed with a bare `mkdir` (`ns_claim_run_dir` in `scripts/lib/run-config.sh`) because two searches started in the same second used to share one; a named `--output-dir` is refused if a job is still in it (`ns_refuse_live_run`) or if it is outside the repo (`ns_refuse_unmounted_run`), since `-v $REPO_ROOT:$REPO_ROOT` is every container's only mount.
- A failed evaluation scores `FAILURE_OBJECTIVE`, which PolyChord maximizes - correct for the algorithm failing, wrong for a dead worker, so the two are kept apart (`WORKER_DIED` in `common.py`). Runs checkpoint and restart themselves; `docs/robustness.md` is the authority on all of it (what is scored, the meqserver bounds, `run_with_retries`, the stall watchdog, `./ri resume`). Three sharp edges worth knowing before reading it: PolyChord's dead-point count is frozen between checkpoint writes - hours at a time - so it is the wrong measure of progress and anything reporting one must carry it forward from the evaluation directories (`dead_points_now`, `_ns_dead_now`); `metrics.json`, `summary.json` and `chains/*.resume` each had a torn-write path that ended a search for good, so records go through `write_json_atomic` and every reader tolerates half a file; and why a run stopped is only ever in its `run.log`, which `run_with_progress` tees as the run goes.
- CI runs only what needs no Docker. The image-dependent self-checks (`--self-check` in each `scripts/lib/nested_sampling` module) run nowhere automatically: `./ri self-check` is the entry point, and it runs the working tree inside the images, so no rebuild is needed to check a change. `scripts/test_watchdogs.py` is the host-side half of the deadlock-watchdog checks and does run in CI. `./ri self-check self-heal` is the only check that starts a real search and breaks it (~5 minutes, throwaway directories); every bug found in the retry machinery so far passed the fixtures and failed that kill. Shell self-checks run under `set -e`, which exempts a negated command - a `! cmd` assertion can never fail, so write negative assertions as `cmd && { echo "FAIL: ..."; exit 1; }`. CI's shellcheck covers `scripts/lib/*.sh` at default severity, so an *info*-level finding fails the build; it is not installed on this host and `./ri self-check` does not run it, so run `shellcheck -x scripts/*.sh scripts/lib/*.sh` before shipping shell.
- Every image must byte-compile its interpreter's stdlib at build time. Check a new base image by counting its stdlib `.pyc` files.
- Benchmark direct stage timings before end-to-end A/B confirmation. Effects below 0.1s need at least 30 interleaved pairs; check host load and use `timeout` because MeqTrees can hang.
