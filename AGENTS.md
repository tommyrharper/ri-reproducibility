# Project agent memory

**This repo's purpose: run nested sampling (PolyChord) over the parameter space of R2D2 and WSClean to find their failure modes.** Everything else (Docker images, smoke tests, pinned upstream revisions) exists to serve that. It is not a paper-reproduction or benchmarking harness.

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `./ri` (the `ri` file at the repo root) is the front door and the only entrypoint users are pointed at: stdlib `argparse` that turns flags into the environment variables `scripts/lib/defaults.sh` already reads, then dispatches into `scripts/`. It holds no behaviour - new behaviour goes in a script, with a subcommand added in `ri` and a case in `scripts/test_cli.py`. `./ri --dry-run <command>` prints what it would run.
- Nested-sampling infrastructure, run commands, and the per-stage profiler (`./ri profile <run>`) are documented in `docs/nested-sampling.md`; use those entrypoints instead of ad hoc container wiring.
- The `polychord` and `meqtrees` images both bake in files from `scripts/lib/nested_sampling` at build time (no live mount); after editing those files, rebuild every image that copies them (`scripts/build.sh polychord`, `scripts/build.sh meqtrees`) before starting a nested-sampling run, or it silently runs the stale baked-in code (`./ri search` and `./ri resume` both build first, so this bites a run started any other way, or one resumed with `--no-build`). The exception is `r2d2_serve.py`, which the R2D2 sidecar runs off the repo bind mount, so it needs no rebuild. `polychord` copies the whole directory, `meqtrees` only the three simulate-side scripts (`simulate_point_source_ms.py`, `point_source_forest.py`, `ms_to_r2d2_mat.py`) - except that the `meqtrees` build also bind-mounts `common.py` and `defaults.toml` to bake the MS skeleton cache, so a parameter-space change (`[[parameter_space]]` in `defaults.toml`, the one authoritative copy) needs both images rebuilt.
- `scripts/build.sh` hashes each image's build inputs into an `ri.build-inputs` label and skips `docker build` when nothing changed (~0.08s), so rebuilding freely is cheap; the input list lives in `build.sh` and must be updated whenever a Dockerfile starts copying something new.
- Host `__pycache__` is excluded from both the context (root `.dockerignore`) and the build-input hash, so a `--self-check` does not force a rebuild.
- Image tags are shared across worktrees. Capture `docker images -q <tag>` per timing run and rebuild all images before trusting a result if another session could have rebuilt one.
- Memory, not CPU, caps a run: ~3.4GB per R2D2 rank (~0.2GB per WSClean rank), linear in `NS_MPI_PROCS` and independent of `NS_NLIVE`, so raise `--nlive` freely and size `--mpi-procs` to fit. `scripts/lib/rank-budget.sh` clamps and reserves against free memory. Sessions share this host, so expect another session's run to shrink yours - which is why `./ri health` with no argument reports *every* run being driven anywhere on the host - ranks running, or a `docker exec` client still starting them, which is minutes of an R2D2 search holding 53GB of workers before its first evaluation (found in the process list, so another worktree's run is reported too, named by a `path` line; a run with no client and no ranks is `STOPPED` and offered `./ri resume` however recently it wrote - a recent evaluation used to read as `STARTING`, which gave a run killed a second ago ten silent minutes; every status there is decided by the *absence* of something, which is also what an unrelated directory looks like, so both `./ri health` and `./ri runs` first require one of `run.env`, `run.log`, `summary.json`, `evaluations/` or `chains/` (`is_run_directory`) rather than headlining any directory `STOPPED` and offering a `./ri resume` that refuses it for having no `run.env`), and why the default run directory is claimed with a bare `mkdir` (`ns_claim_run_dir` in `scripts/lib/run-config.sh`) rather than assumed: two searches started in the same second used to share one, and write each other's evaluations, FIFOs and `summary.json`. A named `--output-dir` cannot be claimed that way, so both run scripts refuse one a job is still in (`ns_refuse_live_run`, on the same `ns_run_is_live` process check `./ri resume` uses) - `mkdir -p` cannot see a live run, and starting into one deletes its FIFOs and overwrites its checkpoint. It must also be inside the repo (`ns_refuse_unmounted_run`): `-v $REPO_ROOT:$REPO_ROOT` is every container's only mount, so a run directory outside it is written half on the host and half inside the containers, and dies on evaluation 1. RSS hides the squeeze, because it excludes swap: `./ri health` reports what the kernel pushed out per run, and warns on a worker that is mostly on disk only while `/proc/pressure/memory` says something is waiting on those pages - being swapped out and being read back are different things, and the second is the one that costs evaluation time (and never fails). Sidecars a killed run left holding memory are removed by the next run before it sizes itself (`ns_reap_leaked_sidecars`), so `./ri health` naming them is a report, not a chore - but "killed" means the run, not the shell that launched it: killing the run script leaves the ranks going (they are children of `containerd-shim`), so each sidecar carries an `ri.run-dir` label and a container whose labelled run is still live is never reaped, whatever the launcher pid in its name says. What such a run *has* lost is `run_with_retries`, invisible in every other number, so `./ri health` warns when a run's `docker exec` client no longer has a run script for a parent; the stall watchdog, which used to leak the same way on a Ctrl-C, is now stopped from an EXIT trap in `run_with_progress`.
- A failed evaluation scores `FAILURE_OBJECTIVE`, which PolyChord maximizes - correct for the algorithm failing, wrong for a dead worker, so the two are kept apart (`WORKER_DIED` in `common.py`): a worker that dies, or goes silent past the reply timeouts next to it, is killed, retried, and then stops the run instead of being scored. That includes a worker that died while nothing was talking to it - the OOM killer's usual victim on this host, and the case where the pipe is already broken when the next request is written: `worker_send` in `common.py` reports the failed write as a dead worker rather than letting `BrokenPipeError` unwind into `abort_run`, which used to end the whole job and spend a restart over one worker. MeqTrees deadlocking with its meqserver (roughly once in 2,000-5,000 evaluations) is caught before that, inside the worker: `PREDICT_WAIT_SECONDS` in `simulate_point_source_ms.py` bounds the predict Timba would otherwise wait on forever, and the worker replaces its own meqserver in ~0.2s rather than holding every rank in PolyChord's collective. An evaluation that hit one leaves a `meqserver-wedged.log`. Runs checkpoint, and `run_with_retries` in `scripts/lib/progress-bar.sh` restarts a run that died in place (`NS_RETRIES`, default 2) - but only while the failed attempt scored evaluations, so a deterministic failure stops at once (dead points are the wrong measure here: PolyChord's count is frozen between checkpoint writes, so it reads zero for a run that has been imaging for an hour). Each restart re-clamps its rank count through `ns_budget_ranks` for the same reason `./ri resume` does - the number was the memory guard's output when the run started, and replaying it onto a host another session has since filled restarts straight into the OOM killer - and stops the run outright when not even one rank fits. That budget counts failures that come straight back rather than restarts ever made - an attempt that ran `NS_RETRY_RESET_SECONDS` (1800) before dying hands it back, or a multi-day search that healed itself twice on day one is out of retries for the rest of the week. Each restart appends to the run's `restarts.log`, and so does `./ri resume` (`<stamp> resumed at N evaluations` against a restart's `<stamp> exit N after M evaluations`) - `./ri health` reports the two on separate lines, adds what is *left* of the budget to the `restarts` line of a run that is still going (`; 1 of 2 left`, or `; 2 of 2 used, so the next crash stops the run until someone resumes it`, replaying the reset and the resume rules over the same log rather than being told, since the counter only exists in the retry loop's shell), and reads the same file to know which gaps between evaluations were the run *not running* and take them out of the span every rate, occupancy and forecast is measured over. Before that it divided by wall clock, so a resumed WSClean run that did 64 evaluations in 17 seconds of work either side of a 4h16m stop read as `0.2/min`, 0% occupancy and a stall costing 100% of the run; `history` and `occupancy` deliberately stay on wall clock, because a stop is part of the shape they exist to show, and the `stalls` line says "of running time" for the same reason. The one CPU figure in the report that covers work this project did not start is the host block's `load` line (`/proc/loadavg` over 1/5/15 minutes against the core count): a run's own `resources` line only measures itself, so without it "my run got slower and every number looks fine" has no answer when the cause is another session. Shown and never warned on - this host runs at every core busy by design, so a 16-rank R2D2 search sits at load 16-17 of 20 with nothing wrong. The sidecar containers are started once, in front of that loop, so before a retry `run_with_retries` calls `sidecar_restore` (`scripts/lib/start-sidecars.sh`, which records each container's own `docker run` arguments) to start any that has gone away again under the same name - without it, a container removed mid-run made every later attempt `docker exec` into a name that no longer existed, score nothing, and hit the anti-spin guard. `run_with_retries` only sees a run that *exits*, so `_ns_stall_watchdog` (same file) covers the one that hangs instead - a rank stuck in an MPI collective burns every core forever with no status for anything to act on - by killing a run that finishes no evaluation in `NS_STALL_TIMEOUT` (7200s, `--stall-timeout`; well clear of `IMAGING_REPLY_TIMEOUT`'s 3600s single-evaluation ceiling, against a measured worst gap of 23.5s on a live R2D2 search). Its timeout is recorded in `run.env` like every other setting, so a resume replays it rather than silently restoring the default, and `./ri health` can tell a stalled run that the watchdog is N minutes away, that `--stall-timeout 0` turned it off, or - past a poll of the timeout - that none is left to kill it. The kill is by command line (`ns_run_process_pattern`, shared with `./ri resume`'s liveness guard) because the pid the run script holds is the `docker exec` client and the ranks are children of `containerd-shim`. An evaluation whose `metrics.json` does not parse - a rank killed mid-write, or a full disk - is treated like one that was still in flight: `read_evaluation_record` in `common.py` warns and skips it and `adopt_completed_evaluations` deletes the directory, because raising there ended a search for good (every restart and every `./ri resume` read the same file and died before scoring anything, so the retry loop gave up too - reproduced by zeroing one file out of 966). Records are written under `metrics.json.partial` and renamed into place, which closes the window for new runs; the tolerance is for the runs already on disk. A truncated `chains/*.resume` - what a rank killed mid-checkpoint-write leaves - was the same trap one level up: PolyChord aborts in Fortran before evaluation 1, so the anti-spin guard stopped the run and every later `./ri resume` died in the same place, with every scored evaluation unreachable on disk (reproduced by truncating a real 44KB file). `run_with_retries` now moves the checkpoint - the one input a restart can change - to `*.resume.unreadable` and retries, which starts the sampler from scratch and replays every scored evaluation out of the point cache without imaging any of them; only on the evidence of a `read_write.F90` gfortran error in *that attempt's* slice of run.log, because a missing image scores nothing too and a good checkpoint thrown away costs a long search its sampler position. A restart adopts the previous attempt's evaluations unconditionally, never gated on PolyChord's `.resume` file - PolyChord writes that only at its first checkpoint, so gating it made a restart before then collide with its own eval directories, and because the likelihood is called from Fortran one rank's traceback hangs every other rank forever; anything unexpected in the likelihood therefore ends in `abort_run` (`MPI_Abort`) rather than a raise. A run with no `summary.json` stopped early: `./ri runs` lists those (the HTML report cannot - it globs for `summary.json`) and `./ri resume <run>` continues one from its own recorded `run.env` - every setting verbatim except the rank count, which goes back through `ns_budget_ranks` because that number was the memory guard's output rather than anyone's choice, and the host it fitted yesterday is another session's today (PolyChord's checkpoint carries live points, not ranks, so 3 ranks resuming at 1 finishes normally). A *live* run has no `summary.json` either, so both `./ri runs` and `./ri health` tell it apart by its processes, and `./ri resume` refuses one - a second job over the same checkpoint corrupts both. `./ri health` is the in-flight question instead - progressing, stalled, or scoring nothing but `FAILURE_OBJECTIVE`, which PolyChord maximizes, so a broken imager reads as a spectacular discovery. Both `./ri runs` and `./ri health`'s stopped warning split those by whether PolyChord left a `.resume` file, because only then does a resume *continue* - without one the sampler starts over, keeping the scored evaluations out of the point cache and deleting the unscored directories (`adopt_completed_evaluations`), which is also why `./ri runs`' `EVALS` counts `metrics.json` files rather than `eval-*` directories: three startup deaths here advertised 7, 7 and 15 evaluations that resuming keeps none of. It also names sidecars a dead run left holding memory. Read-only and free to run against a live search; docs/nested-sampling.md, "Is the run healthy?". PolyChord rewrites `chains/` only every `nlive` dead points *or more* (measured over two throwaway WSClean searches: 22-36 at `--nlive 20`, 51-92 at `--nlive 50`, never under `nlive`, largest for the write that ends the run) - two hours at a time on a 16-rank R2D2 search - so its dead-point count is frozen between writes and anything reporting progress from it must carry it forward across that interval from the evaluation directories (`dead_points_now`, `_ns_dead_now`); `stage` reports the raw count with its age and where it next lands as a floor (`next at 392+`, not `~392`) precisely so nobody reads either as current, and `at risk` reports the other half of that interval - the evaluations scored since the checkpoint and the imaging time behind them, which a restart or a `./ri resume` redoes from nothing (measured: a killed WSClean search shared every pre-kill evaluation with a same-seed uninterrupted control and none of the 146 it scored after the resume, because a resume re-seeds and then skips ahead, so the point cache answers a from-scratch restart but never a resume; four hours of it on the live R2D2 search, and reported without a warning because nothing can be done about it). The forecast's *total* is as stale as that checkpoint too, so a carried count can overtake it: rather than the `~100% done, ~452 of ~452` and no hours left that the live R2D2 search printed for three hours while still sampling, `./ri health` says `past its ~452 dead-point estimate ... revised by the next one` (an explicit `--max-ndead` keeps the ordinary words - it is a hard stop, so 100% of it is true). Why a run stopped is only ever in its `run.log`, which `run_with_progress` tees as the run goes - no other artifact records it.
- CI runs only what needs no Docker. The image-dependent self-checks (`--self-check` in each `scripts/lib/nested_sampling` module) run nowhere automatically: `./ri self-check` is the entry point, and it runs the working tree inside the images, so no rebuild is needed to check a change. `scripts/test_watchdogs.py` is the host-side half of the deadlock-watchdog checks and does run in CI. `./ri self-check self-heal` is the only check that starts a real search - it SIGKILLs one, SIGSTOPs a rank of another (the hang the retry loop cannot see), SIGKILLs a third started with `--retries 0`, SIGKILLs a fourth's workers from inside their sidecar, and `docker rm --force`s a fifth's sidecar container, asserting the first two heal themselves, that the third, which cannot, is headlined `STOPPED` by `./ri health` and then continued to completion by the `./ri resume` line the report itself prints (typed verbatim, since which of the two forms is right depends on where the run directory is), that the fourth finishes with no restart at all, and that the fifth's removed container is started again so its restart has somewhere to land, then truncates that fifth run's PolyChord checkpoint and resumes it (no sixth search - the break needs no live run) to assert the sampler starts over rather than dying on the file again; ~5 minutes on throwaway directories, and every bug found in the retry machinery so far passed the fixtures and failed that kill. Shell self-checks run under `set -e`, which exempts a negated command - a `! cmd` assertion can never fail, so write negative assertions as `cmd && { echo "FAIL: ..."; exit 1; }`; CI's shellcheck covers `scripts/lib/*.sh` (SC2251) and catches the mistake - it lints at default severity, so an *info*-level finding fails the build, which is how the gate came to be red on main for several commits while every other check was green. It is green again at shellcheck 0.8.0, 0.9.0 and 0.10.0 (the spread apt gives across runner images); the handful of findings it had were all inside `--self-check` blocks, where a sandboxing subshell (SC2030/SC2031) and a stubbed `docker` called only indirectly (SC2317) are the point, so they carry inline `# shellcheck disable=` with the reason rather than being written around. Run `shellcheck -x scripts/*.sh scripts/lib/*.sh` before shipping shell - it is not installed on this host and `./ri self-check` does not run it.
- Every image must byte-compile its interpreter's stdlib at build time. Check a new base image by counting its stdlib `.pyc` files.
- Benchmark direct stage timings before end-to-end A/B confirmation. Effects below 0.1s need at least 30 interleaved pairs; check host load and use `timeout` because MeqTrees can hang.
