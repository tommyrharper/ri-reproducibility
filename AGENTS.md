# Project agent memory

**This repo's purpose: run nested sampling (PolyChord) over the parameter space of R2D2 and WSClean to find their failure modes.** Everything else (Docker images, smoke tests, pinned upstream revisions) exists to serve that. It is not a paper-reproduction or benchmarking harness.

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `./ri` (the `ri` file at the repo root) is the front door and the only entrypoint users are pointed at: stdlib `argparse` that turns flags into the environment variables `scripts/lib/defaults.sh` already reads, then dispatches into `scripts/`. It holds no behaviour - new behaviour goes in a script, with a subcommand added in `ri` and a case in `scripts/test_cli.py`. The one exception is `./ri tui` (`tui/`), a Bubble Tea front end over `./ri runs`, `./ri health` and `./ri search` - the only Go here, and the only command that needs a toolchain the rest of the repo does not. `./ri --dry-run <command>` prints what it would run.
- Nested-sampling infrastructure, run commands, and the per-stage profiler (`./ri profile <run>`) are documented in `docs/nested-sampling.md`, with `docs/run-health.md` for reading a live run, `docs/robustness.md` for what happens when one breaks and `docs/nested-sampling-throughput.md` for why the ranks idled (and why searches now run PolyChord's asynchronous MPI mode by default), why rank 0 is not one of the workers, why a rank past the first few is worth ~40% of one, why WSClean is built for `x86-64-v3` by default (`WSCLEAN_TARGET_CPU`, worth ~9% of the `wsclean` binary against the plain x86-64 baseline, and `--native` is now only a few percent on top), why a source at the phase centre no longer asks MeqTrees for its (constant) predict, why the simulator no longer writes `WEIGHT`/`SIGMA` either (makems already leaves them at 1.0, so the sigma reaches R2D2 as `ms_to_r2d2_mat.py --noise-sigma-jy` out of `simulation.json` - a third of the simulate stage, guarded by `self_check_noise_weighting`), and where the remaining per-evaluation budget goes (86% is the `wsclean` binary - and the 2.2x concurrency inflation is this CPU's all-core clock and hybrid topology, not a memory-bandwidth ceiling - so read any throughput measurement after the first ~4 seconds, which run 20% fast), and why a scored evaluation's `sim.ms` is never written to the disk at all (it is built in `NS_SCRATCH_DIR`, one host tmpfs bind-mounted into every container, and deleted as `metrics.json` is written; only a failed evaluation and `./ri search --keep-measurement-sets` move it back beside the record), and why a resume holds only each adopted evaluation's objective rather than its record (every rank runs the adoption, so keeping the records wanted 62GB on a 62GB host at the target run size), and why a bigger run is a *more* efficient one (utilisation 93.9% at `--nlive 25` and 98.3% at `--nlive 200`, because the unaccounted time is a ~6s per-run startup constant plus 0.8%, not a rate - PolyChord's own sampling is 5us a call at every `nlive`, so do not go looking for idle time again); and `docs/nested-sampling-power-limit.md` for why the host rather than the code is what caps throughput now - the package runs at a 65W RAPL long-term limit against the part's own 117W rating, which is what sets the all-core clock, costs ~26% of the evaluations per second, is raisable only as root, and is the real cause of the burst-clock trap (the limit's averaging window is 8 seconds, not 4); and `docs/nested-sampling-io-placement.md` for where an evaluation's bytes go - the simulator assembles the MS in the destination directory when that is already `NS_SCRATCH_DIR` (`scratch_root_for()`, because a container's own `/dev/shm` and the shared scratch are different mounts, so the closing move was a whole-MS copy: -6.5ms an evaluation), WSClean's `-temp-dir` and its five FITS images are free where they are, `--mpi-procs` above `nproc` buys nothing at a fixed power limit, and A/B arms run *sequentially* on this host produce consistent false positives at the ~4% level - run them simultaneously; and `docs/nested-sampling-evaluation-budget.md` for what one evaluation's ~280ms is made of at production concurrency, reproduced on two seeds straight out of every `wsclean.stdout.log`'s own phase line - 69% is WSClean's clean loop, 20% the path to the first inversion, 11% starting the process (casacore's static initialisers; dropping MPI, Python or HDF5 from the build was measured and buys ~0), 6% simulate and 0.6% metrics, so nothing measurable is left in the harness - plus the simultaneous-arm flag screen that closes off WSClean's own knobs (`-parallel-reordering 1` and `-abs-mem` are worth 0, `-no-reorder` costs 36%, the whole reorder is only 5% and is not reusable across evaluations, and `-wgridder-accuracy 1e-2` is worth +13.8% but must not be taken because `log10_dynamic_range` reaches 1e6) - plus the `/proc/cpuinfo` trap (a *cold* open blocks ~20ms on this kernel and a warm one 0.04ms, so warm it before any rig) and the fact that R2D2 has never been profiled here at all, because `./ri fetch-checkpoints` needs a browser; and `docs/nested-sampling-clean-loop.md` for the one lever that does move the clean loop - `-mgain` sets how deep each minor loop goes, so `-niter 100` buys ~6.5 major cycles at 0.8 and ~4.7 at 0.9, worth +20% evaluations per second, left at `DEFAULT_WSCLEAN_MGAIN = 0.8` because it is result-preserving for the default `total_rms_jy` objective (1e-7 median) but not for `peak_flux_abs_error_jy` or `sigma_res`, and because it is the experiment definition every archived run was scored under; and `docs/nested-sampling-ms-open.md` for the largest item outside the gridding itself - WSClean re-opens the *parent* Measurement Set once per gridding and degridding pass (15.7 times an evaluation) and casacore attaches every subtable on each open, so the simulator now deletes the six nothing reads (`FEED`, `FLAG_CMD`, `HISTORY`, `POINTING`, `PROCESSOR`, `STATE`), worth +14.9% evaluations per second end to end for the first five and another -3.2% on the `wsclean` binary for `FEED`, with bit-identical images - dropped after the predict rather than in the cached skeleton because casacore refuses to open an MS missing a required subtable and MeqTrees needs it opened that way; the avenue is now closed from the simulator's side, because each of the six survivors was dropped on its own and every one kills WSClean, their unused columns cannot be stripped either (casacore's `MS*` classes validate them) and `IncrementalStMan` will not release a main-table column - so the floor is ~1.9ms an open and ~30ms an evaluation, and a `--keep-measurement-sets` MS is one CASA will not open; and `docs/nested-sampling-wsclean-patches.md` for the other half of that item, which is WSClean's - it re-opens the parent MS on every pass only to read the `ANTENNA` table's names, so `docker/wsclean/patches/` now carries a one-function cache for them (`git apply`ed in `docker/wsclean/Dockerfile`, hashed into `ri.build-inputs`, and a `WSCLEAN_GIT_TAG` bump that breaks a patch fails the image build on purpose), worth +10.5% evaluations per second end to end and -13.1% on the `wsclean` binary with bit-identical images - and note that `WSCLEAN_IMAGE` lets two searches A/B two `wsclean` builds simultaneously, and that `NS_MAX_NDEAD` defaults to 12, so a benchmark search that forgets `--max-ndead` finishes in four seconds; and `docs/nested-sampling-wsclean-zygote.md` for the largest item that is not imaging arithmetic at all - 27ms of every 163ms `wsclean` process runs before `main()` does, initialising the same 73 shared objects (casacore's chain is 11.4ms of a 14.8ms `wsclean --version`), so `docker/wsclean/src/zygote.cpp` is a fork server that pays it once per rank and forks an already-initialised child per evaluation (`zygote_run()` in `common.py` replaces `sidecar_run()` on the WSClean path and keeps its retry shape; `./ri self-check zygote` covers the protocol), worth +8.4% evaluations per second end to end with bit-identical images - and note that `image_binary_seconds` and `peak_memory_bytes` now come from the zygote's `wait4()` rather than a forked `/usr/bin/time`, so they are no longer quantised to 10ms and an archived run's `image_binary` column is ~5ms low against a run made since. and `docs/nested-sampling-phase-profile.md` for where a post-zygote evaluation's 191ms actually goes and how to look for yourself - every evaluation now runs `wsclean -log-time` (measured free against a 1.8%-resolution null pair), so `./ri profile <run> --phases` turns any run's own logs into a phase table with no rig: 84% of an evaluation is the `wsclean` binary and 21ms is everything else the harness does, and inside the binary 48% is ducc0's 8.5 gridding and 6.5 degridding passes (per-call setup, not arithmetic, so the only lever is `-mgain`), 10% deconvolution, 21% metadata and I/O, and 6.7% is fitting the Gaussian beam to the PSF - the largest non-imaging item, paid twice per evaluation because this parameter space's fitted beam is ~1.75x the theoretical estimate that sizes the fitting box, and not movable without changing the restored image; the same page closes pre-warming the zygote parent (0.94ms of process-global casacore state, not the ~11ms the zygote doc estimated) and WSClean's four remaining parent-MS opens (0.51ms each over a plain casacore `Table`); and `docs/nested-sampling-cost-model.md` for why a run's throughput falls as it goes and where that says to look next - an evaluation costs `100.4ms + 5.64us x visibilities` at production concurrency (fitted over 34368 evaluations) and nested sampling compresses towards the long-observation, many-channel corner, so evaluations/second drops ~15% over six minutes with nothing degrading (`./ri profile <run> --over-time` shows it on any run), and the *fixed* half of an evaluation shrinks in share as a run goes deeper (60% at the median, 55% by the end), which makes pass-count levers (`-mgain`) worth more than the metadata ones five iterations have been spent on - the same page ships `-data-column DATA` (WSClean was opening the whole parent MS only to look for a `CORRECTED_DATA` column the simulator never writes: -1.0% on the `wsclean` binary over 800 paired replays against a 0.1%-resolution null, 1000 FITS data blocks identical, guarded by `self_check_dropped_subtables()`) and closes `-gridder tuned-wgridder` (ducc0: no appropriate kernel), `-gridder wtowers` (not built) and the beam fit's thrown-away first fit (the retry triggers iff fitted > 1.25x theoretical, independent of `-beam-fitting-size`, and fit 2 is seeded by fit 1); and `docs/nested-sampling-simulate-stage.md` for the harness half of an evaluation - the MeqTrees stage was 8.4% of a run's worker time and a fifth of that was work with no consumer (the DATA column read back only for its shape, `determine_corr_selection`'s second open of the same table, the six unused subtables copied out of the skeleton cache only to be deleted, and three whole copies of DATA allocated to add noise to it), so it is now -20% at production concurrency over two swapped pairs of simultaneous searches with a bit-identical Measurement Set - the same page records that `./ri profile --phases` has to be read on *medians* (the beam fit is 10.6ms on the mean and 6.25ms on the median, so it is not the largest non-arithmetic item; WSClean's two parent-MS opens before the imaging table are, at 8.8% of an evaluation), that there is no ducc0 warm-up for the zygote parent to inherit, and that nothing measurable is left in the simulate stage; and `docs/nested-sampling-shared-ms-open.md` for the end of that avenue - a `wsclean` run constructs a `casacore::MeasurementSet` over its input *five* times before it reads a visibility (counted with a 30-line `LD_PRELOAD` shim over `open64`, no rebuild and no profiler), so `patches/0003` hands out a copy of one open handle instead: 21 `table.dat` opens down to 4, -3.7% on the `wsclean` binary over 1600 interleaved tmpfs replay pairs against a 0.03% null and -4.4%/-6.1% over two simultaneous swapped searches, 800 FITS data blocks identical - and note that the cache is deliberately leaked because casacore's own static table cache is destroyed first and the process would die in its exit handlers *after* writing correct images, which only a non-zygote `wsclean` would ever show; and `docs/nested-sampling-fftw-planner.md` for the one after that, which is not casacore's - a `wsclean` process asks FFTW for 63 transform plans and keeps none (`schaapcommon`'s `Convolve()` builds and destroys four 1-D plans on every call, `Resampler` two 2-D ones per gridding and degridding pass), 6.3ms of a ~56ms process, of which 4.4ms is the once-per-size build that is process-global state - so `WarmFftwPlanner()` in `docker/wsclean/src/zygote.cpp` builds the twelve plans in the fork server's parent and every child inherits them: -6.9% on the `wsclean` binary in an interleaved tmpfs replay against a -0.2% null, -5.0% over four simultaneous swapped searches, 400 FITS data blocks identical, and note the four warmed sizes (108, 128, 142, 156) are derived from `DEFAULT_IMAGE_DIM = 128` and a stale list costs the speedup rather than a result; and `docs/nested-sampling-gridder-floor.md` for where the *other* 58% goes and why the harness-side mining is finished - ducc0 reports its own timer tree if you change one hard-coded `0` to a `2` in `wgridder/wgriddingmsgridder.cpp`, and it prices a pass at 57% gridding proper, 23% FFT, 11% corrections and 3% index, i.e. arithmetic, while every pass builds a six-plane w-cube for a w-range spanning 0.7% of one plane (`nplanes = (wmax-wmin)/dw + supp`, and all 104 Measurement Sets of a real corpus report `grid=(154x154x6)`) - turning that off is **-29% on the `wsclean` binary** but perturbs the restored image by 2.3e-5 of its peak, so it is priced there as a decision rather than taken; the same page ships `docker/wsclean/patches/0004`, a `schaapcommon` plan cache taking 64 FFTW plan builds an evaluation down to 12 (-2.7% in an interleaved tmpfs replay, -3.2% over four simultaneous swapped searches, 520 FITS data blocks identical), and records that two arms' FITS files never byte-compare equal because the header carries the `-name` path - compare data blocks; and `docs/nested-sampling-row-blocks.md` for the last non-arithmetic item, the reorder - WSClean reads its input Measurement Set a row at a time (13 casacore column reads a row, four of them re-reading what `NextRow()` just discarded, plus a whole extra pass over `TIME` for a timestep count only baseline-dependent averaging wants) and a tiled column costs ~10x more read that way than in blocks, so `patches/0005` gives the row providers one forward-only block: 29484 column reads an evaluation down to 27 `getColumnRange()` calls, -48% of the reorder phase, -2.2% on the `wsclean` binary in an interleaved tmpfs replay against a 0.02% null and -4.1% over four simultaneous swapped searches, 530 FITS data blocks identical - a 256-row block already has all of it, the block is copied rather than referenced because `NoiseMSRowProvider` mutates what it is handed, and a set whose rows differ in shape falls back to a single row (verified identical, 7.8% slower); and `docs/nested-sampling-process-warm-up.md` for the 5ms a forked child spends between its version banner and `=== IMAGING TABLE ===` - a throwaway `TMARK` patch splits it into `fits_init_cfitsio()` (0.47ms) and the first `casacore::MeasurementSet` construction (3.8ms, of which ~1.5ms is process-global; the measures conversion inside `getObservationInfo()` is 45us), so `zygote.cpp` now pays both in the parent - the phase falls 7.15ms to 4.78ms in all eight of eight swapped simultaneous pairs against a flat in-log null, -1.9% on the child over 230 interleaved replay pairs, 230 FITS data blocks identical - and the same page records that WSClean fits its restoring beam on a quarter of the box it means to use, because `(xi - x_mid)` in `schaapcommon`'s Gaussian fitter is unsigned arithmetic (75.3% of model evaluations underflow to 0): a real failure mode, not result-preserving to fix, and the bit-identical half of it is worth 1%.; and `docs/nested-sampling-disk-footprint.md` for the constraint that is not the clock - an evaluation directory was 393.6KB with the `sim.ms` already pruned and 94% of that was FITS, of which WSClean's `model` and `psf` have never had a reader at all and its `dirty` and `residual` are read once, by `compute_image_metrics()`, before the record is written, so all four now join `PRUNED_ARTEFACTS`: **99.9KB an evaluation, 3.94x**, for 48.5us of `unlink()`, taking this host's ceiling from 477k evaluations to 1.88M and making the wall clock the binding constraint on a single search again - the same page records that `evaluations/` needs no sharding (flat ~45us to create the 400000th directory) and that a run is `~17 x nlive x num_repeats` evaluations. Nothing measurable is left outside ducc0's arithmetic. Use those entrypoints instead of ad hoc container wiring.
- The `polychord` and `meqtrees` images both bake in files from `scripts/lib/nested_sampling` at build time (no live mount); after editing those files, rebuild every image that copies them (`scripts/build.sh polychord`, `scripts/build.sh meqtrees`) before starting a nested-sampling run, or it silently runs the stale baked-in code (`./ri search` and `./ri resume` both build first, so this bites a run started any other way, or one resumed with `--no-build`). The exception is `r2d2_serve.py`, which the R2D2 sidecar runs off the repo bind mount, so it needs no rebuild. `polychord` copies the whole directory, `meqtrees` only the three simulate-side scripts (`simulate_point_source_ms.py`, `point_source_forest.py`, `ms_to_r2d2_mat.py`) - except that the `meqtrees` build also bind-mounts `common.py` and `defaults.toml` to bake the MS skeleton cache, so a parameter-space change (`[[parameter_space]]` in `defaults.toml`, the one authoritative copy) needs both images rebuilt.
- `scripts/build.sh` hashes each image's build inputs into an `ri.build-inputs` label and skips `docker build` when nothing changed (~0.08s), so rebuilding freely is cheap; the input list lives in `build.sh` and must be updated whenever a Dockerfile starts copying something new.
- Host `__pycache__` is excluded from both the context (root `.dockerignore`) and the build-input hash, so a `--self-check` does not force a rebuild.
- Image tags are shared across worktrees. Capture `docker images -q <tag>` per timing run and rebuild all images before trusting a result if another session could have rebuilt one.
- Memory, not CPU, caps a run: ~3.4GB per R2D2 rank (~0.2GB per WSClean rank), linear in `NS_MPI_PROCS` and independent of `NS_NLIVE`, so raise `--nlive` freely and size `--mpi-procs` to fit. `scripts/lib/rank-budget.sh` clamps and reserves against free memory, and reaps sidecars a killed run left holding it (`ns_reap_leaked_sidecars`) - "killed" meaning the run, not its launcher shell, which is why each sidecar carries an `ri.run-dir` label and a container whose labelled run is still live is never reaped. Sessions share this host, so expect another session's run to shrink yours. Run directories: the default is claimed with a bare `mkdir` (`ns_claim_run_dir` in `scripts/lib/run-config.sh`) because two searches started in the same second used to share one; a named `--output-dir` is refused if a job is still in it (`ns_refuse_live_run`) or if it is outside the repo (`ns_refuse_unmounted_run`), since `-v $REPO_ROOT:$REPO_ROOT` is every container's only mount.
- A failed evaluation scores `FAILURE_OBJECTIVE`, which PolyChord maximizes - correct for the algorithm failing, wrong for a dead worker, so the two are kept apart (`WORKER_DIED` in `common.py`). Runs checkpoint and restart themselves; `docs/robustness.md` is the authority on all of it (what is scored, the meqserver bounds, `run_with_retries`, the stall watchdog, `./ri resume`). Three sharp edges worth knowing before reading it: PolyChord's dead-point count is frozen between checkpoint writes - hours at a time - so it is the wrong measure of progress and anything reporting one must carry it forward from the evaluation directories (`dead_points_now`, `_ns_dead_now`); `metrics.json`, `summary.json` and `chains/*.resume` each had a torn-write path that ended a search for good, so records go through `write_json_atomic` and every reader tolerates half a file; and why a run stopped is only ever in its `run.log`, which `run_with_progress` tees as the run goes.
- CI runs only what needs no Docker. The image-dependent self-checks (`--self-check` in each `scripts/lib/nested_sampling` module) run nowhere automatically: `./ri self-check` is the entry point, and it runs the working tree inside the images, so no rebuild is needed to check a change. `scripts/test_watchdogs.py` is the host-side half of the deadlock-watchdog checks and does run in CI. `./ri self-check self-heal` is the only check that starts a real search and breaks it (~5 minutes, throwaway directories); every bug found in the retry machinery so far passed the fixtures and failed that kill. Shell self-checks run under `set -e`, which exempts a negated command - a `! cmd` assertion can never fail, so write negative assertions as `cmd && { echo "FAIL: ..."; exit 1; }`. CI's shellcheck covers `scripts/lib/*.sh` at default severity, so an *info*-level finding fails the build; it is not installed on this host and `./ri self-check` does not run it, so run `shellcheck -x scripts/*.sh scripts/lib/*.sh` before shipping shell.
- Every image must byte-compile its interpreter's stdlib at build time. Check a new base image by counting its stdlib `.pyc` files.
- Benchmark direct stage timings before end-to-end A/B confirmation. Effects below 0.1s need at least 30 interleaved pairs; check host load and use `timeout` because MeqTrees can hang.
