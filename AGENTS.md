# Project agent memory

**This repo's purpose: run nested sampling (PolyChord) over the parameter space of R2D2 and WSClean to find their failure modes.** Everything else (Docker images, smoke tests, pinned upstream revisions) exists to serve that. It is not a paper-reproduction or benchmarking harness.

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `./ri` (the `ri` file at the repo root) is the front door and the only entrypoint users are pointed at: stdlib `argparse` that turns flags into the environment variables `scripts/lib/defaults.sh` already reads, then dispatches into `scripts/`. It holds no behaviour - new behaviour goes in a script, with a subcommand added in `ri` and a case in `scripts/test_cli.py`. The one exception is `./ri tui` (`tui/`), a Bubble Tea front end over `./ri runs`, `./ri health`, `./ri profile` and `./ri search` - the only Go here, and the only command that needs a toolchain the rest of the repo does not. `./ri --dry-run <command>` prints what it would run.
- Nested-sampling infrastructure, run commands, and the per-stage profiler (`./ri profile <run>`) are documented in `docs/nested-sampling.md`, with `docs/run-health.md` for reading a live run and `docs/robustness.md` for what happens when one breaks; use those entrypoints instead of ad hoc container wiring. A run's `summary.json` is the marker that says "finished" to every reader (resume, merge, listing, report), so a run still going must never be given one: `./ri report --live` and `./ri plot gui --live` read what it has written so far, through the `summary.live.json` that `scripts/live_runs.py` writes beside it.
- Speed: `docs/nested-sampling-speed.md` is the index for all of it - what shipped, what each change was worth, and which of the twenty pages under it holds the evidence. Read it before attempting any throughput work; thirty-three rounds have already closed most of the obvious avenues with numbers, and it names the two open ones (R2D2 U-Net inference; WSClean, where CSD3's ~40x larger evaluations made ducc0 and the reordered-file reads worth patching again - docs/csd3-speed.md, rounds 23-24). Measure with `./ri bench`: every finished search appends a row to `benchmarks.jsonl`, grouped by commit, machine, image ids and settings, and `./ri bench run <imager> --repeat 3` is the controlled version - warmed up, synchronous and seeded, none of which is optional here (`docs/nested-sampling-benchmarks.md` has the numbers behind all three). Two things this host makes non-negotiable: an A/B needs `--interleave <SETTING> A B` so the arms alternate rather than run as blocks, and a three-repeat control spans ~5%, so anything smaller than that is not visible end to end - time the stage directly instead. A short arm's `evals_per_s` also carries its start-up (23-88s on a GPU node) and any whole-search stall (PolyChord's root used to block 20-45s in a Lustre create of `chains/*_temp.resume`, stopping every rank; round 225, fixed in 227 by writing `chains/` on tmpfs with a Lustre mirror, `NS_CHAINS_TMPFS=0` to compare), which can halve a 3-minute arm, so short arms compare `steady_evals_per_s`, which cuts both (docs/csd3-speed.md, round 211). Four sharp edges from it bite outside speed work: both imagers are patched locally (`docker/wsclean/patches/` and `docker/r2d2/patches/`, `git apply`ed in each Dockerfile and hashed into `ri.build-inputs`, so a `WSCLEAN_GIT_TAG` or `R2D2_GIT_REF` bump that breaks a patch fails the image build on purpose; PolyChord has one too, `docker/polychord/patches/`, opt-in via `NS_ADOPT_CONTOUR=1`, round 312) and every evaluation runs through a fork server (`docker/wsclean/src/zygote.cpp`, `zygote_run()` in `common.py`, which replaced the old per-command sidecar shell; `./ri self-check zygote` covers the protocol); `NS_MAX_NDEAD` defaults to 12, so a benchmark search that forgets `--max-ndead` finishes in four seconds; archived runs are not comparable with new ones (any evals/s figure from before iteration 18 is about half the current rate, and an old `image_binary` column is ~5ms low); and A/B arms must run *simultaneously* - `WSCLEAN_IMAGE` exists so two searches can race two builds - because sequential arms give consistent ~4% false positives here.
- This branch (`cluster`) runs without Docker: the four images are carried to CSD3 as Apptainer SIFs (`./ri images export` on a Docker host, `./ri images import` on the cluster; `docs/cluster.md` is the authority). On a login node `./ri search` and `./ri resume` claim the run directory and submit themselves as a Slurm job named after it (`scripts/lib/slurm.sh`; `NS_SBATCH=0` runs in place), and a run is live while a job of its name is queued (`ns_run_is_live` asks `squeue`, and so do `./ri health` and `./ri runs`), because pgrep on the login node sees nothing. A run binds the working tree's `scripts/lib/nested_sampling` over the copy baked into `polychord.sif` and `meqtrees.sif`, so editing those files needs no rebuild - but a Dockerfile, patch, or `[[parameter_space]]` change (the `meqtrees` build bakes the MS skeleton cache from `defaults.toml`) still means rebuild, export and import (WSClean patches alone: `./ri images patch-wsclean` in a compute-node job layers them over `images/wsclean.sif` in ~2 minutes, and a SIF has only the patches that existed when it was built - the 21 Sep one stops at 0006, and a WSClean search's job builds a patched copy into `$RI_WORK_DIR/.cache/ri` once and uses it while the SIF lags the tree (`ns_use_patched_wsclean_sif`, +50% evals/s; `NS_PATCH_WSCLEAN=0` for an A/B that wants the stale SIF, docs/csd3-speed.md round 94); to A/B a patch before that, build it in an unprivileged `apptainer --fakeroot` sandbox on a compute node and layer the binaries over the shipped SIF with a `Bootstrap: localimage` SIF - not `APPTAINER_BIND`, which `job-env.sh`'s `env -i` drops - docs/csd3-speed.md, rounds 23 and 26). Apart from that patch layer, `./ri search` and `./ri resume` build nothing; a missing SIF is refused by `ns_require_sifs`. CSD3 sharp edges: its login environment exports `OMP_NUM_THREADS=1`, which sbatch carries into jobs and GNU `nproc` honours, so count CPUs with `env -u OMP_NUM_THREADS nproc`; and the administrators allow one Slurm client call per two minutes and a few CPUs on login nodes, so anything that polls goes through `scripts/slurm_queue.py`'s cache and nothing host-side may size a pool from the core count there (docs/cluster.md, "Being a good citizen"). A third: the RDS project quota is ~1M files, and a 36-rank WSClean benchmark leaves ~20k under `results/`, so delete benchmark runs once their `benchmarks.jsonl` row exists - a full quota kills a search with `EDQUOT` (`quota -s`).
- `scripts/build.sh` hashes each image's build inputs into an `ri.build-inputs` label and skips `docker build` when nothing changed (~0.08s), so rebuilding freely is cheap; the input list lives in `build.sh` and must be updated whenever a Dockerfile starts copying something new.
- Host `__pycache__` is excluded from both the context (root `.dockerignore`) and the build-input hash, so a `--self-check` does not force a rebuild.
- Image tags are shared across worktrees. Capture `docker images -q <tag>` per timing run and rebuild all images before trusting a result if another session could have rebuilt one.
- Memory is linear in `NS_MPI_PROCS` and independent of `NS_NLIVE`, so size `--mpi-procs` to fit; `--nlive` is a precision choice, not a free one - a converged async search needs ~(nlive + 0.41 x workers) live points' worth of evaluations, so a bigger `--nlive` only adds time (rounds 307-308). On this branch R2D2's workers fork from one pool parent and share its checkpoints, so `rank-budget.sh` counts `NS_R2D2_SHARED_MB` once plus `NS_R2D2_MB_PER_RANK` (measured ~4.2GB + ~0.4GB per rank on CSD3; the old ~3.4GB per rank was the Docker host's per-rank copies) and a default CPU run gets one rank per CPU plus one for PolyChord's root, which never evaluates (round 186), ~15% faster than the old 35 x 2 (docs/csd3-speed.md, round 18); WSClean is ~0.2GB per rank. `R2D2_OMP_THREADS` defaults to the rounded-up per-rank CPU share computed from the memory-clamped rank count; on CSD3 that is 1, and 39 x 1 beats 20 x 2 (round 276). Judge any rank or layout A/B on `./ri bench`'s `converging evals/s` at the production nlive (150), not raw evals/s at the bench nlive: more ranks cost PolyChord evaluations, so raw rates overstate them (round 309: +11.7% raw is +6.4% converging). `scripts/lib/rank-budget.sh` clamps and reserves against free memory, and reaps sidecars a killed run left holding it (`ns_reap_leaked_sidecars`) - "killed" meaning the run, not its launcher shell, which is why each sidecar carries an `ri.run-dir` label and a container whose labelled run is still live is never reaped. Sessions share this host, so expect another session's run to shrink yours. Run directories: the default is claimed with a bare `mkdir` (`ns_claim_run_dir` in `scripts/lib/run-config.sh`) because two searches started in the same second used to share one; a named `--output-dir` is refused if a job is still in it (`ns_refuse_live_run`) or if it is outside the repo (`ns_refuse_unmounted_run`), since `-v $REPO_ROOT:$REPO_ROOT` is every container's only mount.
- A failed evaluation scores `FAILURE_OBJECTIVE`, which PolyChord maximizes - correct for the algorithm failing, wrong for a dead worker, so the two are kept apart (`WORKER_DIED` in `common.py`). Runs checkpoint and restart themselves; `docs/robustness.md` is the authority on all of it (what is scored, the meqserver bounds, `run_with_retries`, the stall watchdog, `./ri resume`). Three sharp edges worth knowing before reading it: PolyChord's dead-point count is frozen between checkpoint writes - hours at a time - so it is the wrong measure of progress and anything reporting one must carry it forward from the evaluation directories (`dead_points_now`, `_ns_dead_now`); `metrics.json`, `summary.json` and `chains/*.resume` each had a torn-write path that ended a search for good, so records go through `write_json_atomic` and every reader tolerates half a file; and why a run stopped is only ever in its `run.log`, which `run_with_progress` tees as the run goes.
- CI runs only what needs no Docker. The image-dependent self-checks (`--self-check` in each `scripts/lib/nested_sampling` module) run nowhere automatically: `./ri self-check` is the entry point, and it runs the working tree inside the images, so no rebuild is needed to check a change. `scripts/test_watchdogs.py` is the host-side half of the deadlock-watchdog checks and does run in CI. `./ri self-check self-heal` is the only check that starts a real search and breaks it (~5 minutes, throwaway directories); every bug found in the retry machinery so far passed the fixtures and failed that kill. Shell self-checks run under `set -e`, which exempts a negated command - a `! cmd` assertion can never fail, so write negative assertions as `cmd && { echo "FAIL: ..."; exit 1; }`. CI's shellcheck covers `scripts/lib/*.sh` at default severity, so an *info*-level finding fails the build; it is not installed on this host and `./ri self-check` does not run it, so run `uvx --from shellcheck-py==0.9.0.6 shellcheck -x scripts/*.sh scripts/lib/*.sh` (CI's apt version) before shipping shell.
- Every image must byte-compile its interpreter's stdlib at build time. Check a new base image by counting its stdlib `.pyc` files.
- Benchmark direct stage timings before end-to-end A/B confirmation. Effects below 0.1s need at least 30 interleaved pairs; check host load and use `timeout` because MeqTrees can hang.
- Don't bloat `docs/nested-sampling.md` with lots of stuff. That should remain a concise overview. Instead create new documents when a point isn't central.
